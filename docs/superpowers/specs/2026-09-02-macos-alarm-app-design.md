# Matuta — macOS 알람앱 설계

작성일: 2026-09-02 · 이름 확정: 2026-09-02
상태: 승인됨 — 1단계 구현 계획 작성 완료

---

## 1. 한 줄 요약

macOS 기본 시계 앱의 알람을 계승하되, **어떤 음악 소스로든 깨울 수 있고, 절대 안 울리는 일이 없는** 알람앱. 설정은 최소한으로 두고 신뢰성은 앱이 알아서 책임진다.

이름은 **Matuta**로 확정했다. 마테르 마투타(Mater Matuta)는 로마 신화의 새벽과 아침빛의 여신이며, 그 어근에서 라틴어 *matutinus*(아침의)와 프랑스어 *matin*이 나왔다. 앱스토어·소프트웨어 회사·일반 웹 검색에서 같은 이름의 제품을 찾지 못했다. 상표 데이터베이스는 검증하지 않았으므로, 유료화할 경우 정식 상표 검색이 따로 필요하다.

---

## 2. 배경 — 왜 만드는가

### 2.1 기본 시계 앱의 구멍

macOS Ventura부터 시계 앱에 알람이 들어왔지만 세 가지가 비어 있다.

| 한계 | 내용 |
|---|---|
| 딥 슬립에서 안 울림 | 잠금 상태는 되지만 절전 진입 후엔 알람이 무시된다. 사용자들이 쓰는 우회책이 "자동 절전 끄기"일 정도 |
| 사운드 커스텀 불가 | 내장 벨소리 몇 개뿐. 내 음악·파일 지정 불가 |
| 스누즈·페이드 제어 없음 | 볼륨 페이드인, 스누즈 길이, 출력 기기 제어 전무 |

### 2.2 경쟁 앱 조사 결과

- **Awaken** — 가장 강력한 경쟁자. 메뉴바 상주, Apple Music 재생, 클록 스타일 8종 × 테마 19종, 볼륨·밝기 페이드인. App Store 배포이며 **절전 깨우기는 `AwakenHelper`라는 별도 무료 직접 다운로드로 분리**. 샌드박스가 전원 이벤트를 못 건드리기 때문이다.
- **Alarm Clock Pro 15 (Koingo)** — 비샌드박스 직접 배포. Apple Music 플레이리스트, 인터넷 라디오, Mac 켜기/깨우기, 다중 스톱워치, 이메일 발송. 기능은 많으나 UI가 낡았다.
- **Wakefy** — Spotify 전용 무료. 절전·종료 상태에서 전원을 켠다. 알람을 끄려면 자리에서 일어나 걸어가게 강제.
- **소형 계열** — Sleep Alarm Clock, Wake Up Time Pro, Tiny Alarm, Clock Lite. 예쁘거나 단순하며 절전 깨우기·음악 연동은 약하다.
- **Alarmy** — 미션형 알람의 카테고리 1등이지만 **네이티브 macOS 버전이 없다**. 공식 안내가 에뮬레이터 사용일 정도.

### 2.3 조사에서 나온 결론

1. "기본 앱 계승 + 음악 + 커스텀" 조합은 **Awaken이 이미 점유**했다. 그대로 가면 열위 클론이 된다.
2. macOS 알람의 실제 실패 모드는 iOS보다 훨씬 많다. 아이폰은 스피커가 하나지만 Mac은 **출력이 블루투스 이어폰으로 가 있거나, 볼륨이 0이거나, 뮤트거나, 절전 중**이다. macOS가 출력 기기를 내장 스피커로 되돌리는 알려진 버그도 있다.
3. 그런데 조사한 앱들은 **전부 "일단 울리면 끝"을 가정**한다. 프리플라이트 점검이나 소스 폴백을 하는 앱은 하나도 없었다.

**→ 차별점은 절전 깨우기 단독이 아니라 "울리지 않을 모든 경우를 사전에 제거하는 것"이다.**

## 3. 포지셔닝

### 3.1 목표

- 기본 시계 앱만큼 쉽게 쓰이면서
- 어떤 음악 소스로든 깨울 수 있고
- **울리지 않을 확률을 구조적으로 제거한다**

### 3.2 비목표 (Non-goals)

명시적으로 하지 않기로 한 것들이다.

- **미션형 해제** (수학 문제, 사진 촬영, 걸어가서 끄기) — 검토했으나 제외. 해제는 스페이스바 한 번.
- **범용 스케줄러 / 아침 자동화 런처** — 앱 실행, 탭 복원, 스크립트 실행 등. v1 범위 밖. "알람앱"이라는 정체성을 지킨다.
- **iOS 앱, 동기화** — macOS 전용.
- **클록 스타일·테마 다양화** — Awaken의 강점이지만 따라가지 않는다. 나이트스탠드는 한 가지 스타일만.

### 3.3 배포

**Developer ID 서명 + 공증, 비샌드박스, 직접 배포.** 무료/오픈소스 공개를 상정한다.

App Store를 택하지 않는 이유는 샌드박스가 전원 이벤트 API를 막아서, Awaken처럼 앱과 헬퍼를 2개 바이너리로 쪼개야 하기 때문이다. 그 복잡도는 "쉬움"이라는 최우선 원칙에 직접 타격이다.

단, 나중에 마음이 바뀔 수 있으므로 **권한이 필요한 코드는 `PowerMatuta` 한 곳에만 모아둔다.** App Store로 갈 경우 그 파일만 별도 헬퍼로 떼어내면 된다.

## 4. 설계 원칙

이 네 가지가 이후 모든 판단의 기준이다.

1. **신뢰성은 설정이 아니라 동작이다.** 출력 기기, 폴백 순서, 절전 예약, 볼륨 확보는 전부 앱이 알아서 한다. 토글로 노출하지 않는다.
2. **문제가 있을 때만 말한다.** 정상일 때는 조용하다. 프리플라이트 결과를 대시보드로 만들지 않는다.
3. **사용자는 소스가 6종이라는 사실을 몰라도 된다.** 소스 종류를 고르게 하지 않고, 준 것을 보고 앱이 판별한다.
4. **알람별 동작 설정은 세 개뿐이다.** 볼륨, 페이드인, 스누즈. (이름과 반복 요일은 알람의 정체성이지 동작 설정이 아니다.) 넷째를 추가하고 싶어지면 원칙 1로 돌아간다.

## 5. UI 설계

### 5.1 화면 구성

앱은 창 하나 + 메뉴바 + 두 개의 전체화면 모드로 구성된다.

| 화면 | 역할 |
|---|---|
| 알람 목록 창 | 기본 화면. 알람 관리 |
| 알람 편집 시트 | 목록 행을 누르면 열림 |
| 나이트스탠드 (전체화면) | 잘 때. 큰 시계 + 프리플라이트 결과 |
| 알람 오버레이 (전체화면) | 울릴 때 |
| 메뉴바 | 다음 알람 시각 표시 + 간단 메뉴 |

### 5.2 알람 목록 창

기본 시계 앱을 그대로 계승한다. 행마다 큰 시각, 그 아래 작은 글씨로 요일과 사운드 이름, 오른쪽에 켜기/끄기 토글. 행을 누르면 편집 시트. 하단에 `＋ 알람 추가`. 창 우상단에 🌙 버튼으로 나이트스탠드 진입.

**첫 실행 시 빈 화면을 보여주지 않는다.** 7:00 알람이 꺼진 상태로 하나 미리 들어가 있다.

### 5.3 알람 편집 시트

위에서부터 시각 → 반복 → 사운드 → 볼륨 순서.

**시각**은 타이핑이 기본이다. 드럼 휠 대신 큰 숫자 입력 필드를 두고, `7`만 쳐도 7:00으로 해석한다. ↑↓ 키로도 조절된다. Mac에는 키보드가 있으니 이 편이 훨씬 빠르다.

**반복**은 요일 칩 7개. 아무것도 선택하지 않으면 1회성 알람이다.

**사운드**는 이 화면의 핵심이며 **옴니박스 방식**을 쓴다. 칸이 하나다.

- 파일을 끌어다 놓으면 → 로컬 파일 소스
- 링크를 붙여넣으면 → URL을 보고 Spotify / Apple Music / 라디오 스트림 / 일반 웹 중 무엇인지 앱이 판별
- 글자를 입력하면 → 연결된 모든 서비스에서 동시에 검색하고, 결과를 소스 아이콘과 함께 하나의 목록으로 섞어서 보여준다 (서비스별로 나누지 않는다)

그 아래 최근 사용한 소스가 칩으로 4개 정도 깔린다. 두 번째 알람부터는 칩 클릭 한 번으로 끝난다. 소스별 목록을 직접 뒤지고 싶은 경우를 위해 옴니박스 오른쪽에 작은 `찾아보기` 버튼을 두고, 여기서만 소스별 탭이 나타난다.

선택된 소스가 인터넷을 필요로 하면 **그 자리에서 한 문장으로** 알린다: "인터넷이 필요한 소스입니다 — 실패하면 Radar가 대신 울립니다". 설정 화면으로 보내지 않는다.

**볼륨**은 슬라이더 하나와 체크박스 둘(서서히 커지기, 스누즈 9분)뿐이다.

### 5.4 나이트스탠드

화면 전체가 침대 옆 시계가 된다. 큰 현재 시각, 그 아래 다음 알람까지 남은 시간, 하단에 프리플라이트 결과 배지 한 줄.

정상이면 초록으로 `✓ 스피커 · 볼륨 70% · 절전 깨우기 예약됨`. 문제가 있으면 주황으로 바뀌고 원클릭 수정 버튼이 붙는다 (예: "이어폰으로 나갈 예정이에요 → 스피커로 바꾸기").

마우스를 움직이면 컨트롤이 페이드인하고, 가만두면 사라진다.

### 5.5 알람 오버레이

모든 화면을 전체화면으로 점유한다. 큰 시각, 알람 이름, 지금 재생 중인 소스와 출력 기기.

- **스페이스바 = 완전히 끄기.** 이것이 기본 해제 방법이다.
- **스누즈는 마우스 클릭으로만 가능하다.** 키보드로는 누를 수 없다.

스누즈를 일부러 어렵게 만든 이유가 있다. 미션형 해제를 제외했으므로 "스페이스바 한 번"은 다시 잠들기에도 가장 쉬운 해제법이다. 스누즈에 마찰을 주는 것이 그 유일한 상쇄 장치다. ESC를 비롯한 다른 키는 무시한다.

## 6. 아키텍처

```
Matuta.app  (SwiftUI · Developer ID · 비샌드박스)
├── AlarmStore        알람 목록 영속화 (JSON 파일 하나)
├── Scheduler         다음 발생 시각 계산 + 타이머 + 전원 이벤트 예약
├── PowerMatuta        절전 깨우기. 권한이 필요한 코드는 전부 여기만
├── SoundSource       소스 플러그인 프로토콜
│   ├── BuiltInSource / LocalFileSource   AVFoundation
│   ├── StreamURLSource                   AVPlayer
│   ├── AppleMusicSource                  MusicKit
│   ├── SpotifySource                     딥링크 + 앱 제어
│   └── WebSource                         브라우저 열기
├── PlaybackChain     소스 실패 시 다음으로 넘김 / 백업음 동시 재생
├── AudioGuard        출력 기기 전환 · 볼륨 확보 · 뮤트 해제
├── Preflight         위 상태를 사전 진단
└── AlarmOverlay      전체화면 창 · 키 이벤트 처리
```

### 6.1 경계 설계 의도

**`SoundSource`가 이 설계의 중심이다.** 소스를 6개 지원하는 것이 아니라 인터페이스 하나를 6번 구현하는 것이다. `PlaybackChain`과 `Preflight`는 소스의 구체 타입을 전혀 모른다. YouTube 정책이 바뀌거나 새 서비스를 붙일 때 파일 하나만 추가하면 되고, 나머지 코드는 건드리지 않는다.

**`PowerMatuta`를 분리한 이유**는 §3.3에서 설명한 배포 전환 가능성 때문이다. 권한이 필요한 호출이 앱 전체에 흩어지면 나중에 떼어낼 수 없다.

**`AudioGuard`와 `Preflight`는 같은 상태를 본다.** 차이는 시점뿐이다 — `Preflight`는 자기 전에 읽어서 알리고, `AudioGuard`는 울릴 때 읽어서 고친다. 판정 로직은 공유한다.

## 7. 신뢰성 명세

### 7.1 프리플라이트 점검 항목

| 항목 | 판정 | 조치 |
|---|---|---|
| 시스템 볼륨 | 30% 미만이면 경고 | 원클릭으로 알람 볼륨까지 올림 |
| 뮤트 상태 | 뮤트면 경고 | 원클릭 해제 |
| 기본 출력 기기 | 블루투스·유선 이어폰이면 경고 | 원클릭으로 내장 스피커 전환 |
| 전원 이벤트 예약 | 예약 실패 시 경고 | 재시도, 실패하면 절전 방지로 대체 |
| 소스 상태 | 소스별 `preflight()` 결과 | 소스마다 다름 (§8.2) |

### 7.2 실행 시점

- 나이트스탠드 진입 시 (사용자가 자러 갈 때)
- 알람 30분 전 (조용히, 문제가 있을 때만 알림)

### 7.3 알람이 울릴 때의 순서

1. 현재 출력 기기·볼륨·뮤트 상태를 저장
2. 목표 출력 기기로 전환, 뮤트 해제, 볼륨을 알람 볼륨까지 확보
   - **목표 출력 기기는 항상 내장 스피커다.** 사용자가 고르는 항목이 아니다. 이어폰을 낀 채 잠든 경우에도 스피커로 울려야 하기 때문이다
3. `PlaybackChain` 실행
4. 오버레이 표시
5. 해제되면 저장해둔 오디오 상태를 원상복구

### 7.4 폴백 정책

**백업음**은 내장 사운드 `Radar` 하나로 고정한다. v1에서는 사용자가 바꿀 수 없다 (원칙 1). 아래 두 경우 모두 이 백업음을 쓴다.

소스는 두 부류로 나뉜다.

- **검증 가능한 소스** (내장, 로컬 파일, 스트림 URL, Apple Music) — 재생 실패가 에러로 잡힌다. 실패하면 다음 소스로 순차 폴백하고, 마지막은 항상 내장 사운드다.
- **검증 불가능한 소스** (Spotify, 웹) — 브라우저나 외부 앱이 열렸는지는 알 수 있지만 소리가 났는지는 알 수 없다. 이 경우 **내장 사운드를 낮은 볼륨으로 동시에 깔아둔다.**

동시 재생 방식을 택한 이유는, 시스템 출력을 실제로 측정해서 무음을 감지하는 것도 기술적으로는 가능하지만 권한과 복잡도가 붙기 때문이다. 동시 재생이 훨씬 견고하고 구현이 단순하다. 무음 측정은 필요해지면 나중에 붙인다.

## 8. 데이터 모델과 소스

### 8.1 저장

알람 목록은 `~/Library/Application Support/Matuta/alarms.json` 파일 하나에 저장한다. 데이터베이스는 쓰지 않는다.

```swift
struct Alarm: Codable, Identifiable {
    var id: UUID
    var hour: Int
    var minute: Int
    var weekdays: Set<Weekday>     // 비어 있으면 1회성
    var label: String?
    var source: SoundSourceRef
    var volume: Double             // 0...1
    var fadeIn: Bool
    var snoozeMinutes: Int?        // nil이면 스누즈 없음
    var isEnabled: Bool
}

enum SoundSourceRef: Codable {
    case builtIn(name: String)
    case localFile(bookmark: Data)   // security-scoped bookmark
    case streamURL(URL)
    case appleMusic(id: String)
    case spotify(uri: String)
    case web(URL)
}
```

로컬 파일은 경로가 아니라 security-scoped bookmark로 저장한다. 사용자가 파일을 옮겨도 따라간다.

### 8.2 SoundSource 프로토콜

```swift
protocol SoundSource {
    var requiresNetwork: Bool { get }
    var needsBackupTone: Bool { get }    // 재생 성공을 검증할 수 없는 소스
    func preflight() async -> PreflightResult
    func play(volume: Double, fadeIn: Bool) async throws
    func stop()
}
```

소스별 `preflight()`가 확인하는 것:

| 소스 | 확인 | `needsBackupTone` |
|---|---|---|
| BuiltIn | 없음 (항상 가능) | 아니오 |
| LocalFile | bookmark 해석 가능 여부 | 아니오 |
| StreamURL | HEAD 요청 도달 여부 | 아니오 |
| AppleMusic | 구독·인증 상태, 항목 존재 여부 | 아니오 |
| Spotify | 앱 설치·로그인 여부 | **예** |
| Web | URL 형식만 | **예** |

### 8.3 옴니박스 판별 규칙

입력을 받으면 순서대로 판별한다.

1. 드롭된 파일이면 → `localFile`
2. `spotify:` 스킴이거나 `open.spotify.com` 호스트면 → `spotify`
3. `music.apple.com` 호스트면 → `appleMusic`
4. URL이고 오디오 스트림 Content-Type이면 → `streamURL`
5. 그 밖의 URL이면 → `web`
6. URL이 아닌 텍스트면 → 연결된 서비스 검색 결과를 보여줌

판별 결과는 확정 전에 칩으로 보여주고, 사용자가 다르게 고칠 수 있게 한다.

## 9. Scheduler와 절전 깨우기

`Scheduler`는 두 겹으로 동작한다.

- **앱이 깨어 있을 때** — 타이머로 발화
- **Mac이 절전 중일 때** — `PowerMatuta`가 알람 2분 전에 전원 이벤트를 예약해 Mac을 깨운다

두 겹을 다 두는 이유는 어느 한쪽이 실패해도 다른 쪽이 살아 있기 때문이다.

재계산 시점: 앱 시작 시, 알람이 추가·수정·삭제될 때, 절전에서 복귀할 때, 시스템 시간대가 바뀔 때.

**미해결 사항이 하나 있다.** `IOPMSchedulePowerEvent`가 관리자 권한을 요구하는지가 확실하지 않다. 요구한다면 권한 헬퍼를 한 번 설치하는 절차가 생기고 그것은 "쉬움" 원칙에 직접 타격이다. 따라서 **구현 순서상 이것을 가장 먼저 최소 코드로 검증하고**, 결과에 따라 온보딩 설계를 확정한다. 권한이 필요한 것으로 밝혀지면 대안은 두 가지다: (a) 최초 1회 권한 요청 후 헬퍼 설치, (b) 알람 전후로만 절전을 막는 방식으로 대체. 검증 결과를 보고 고른다.

## 10. 테스트 전략

시스템에 의존하는 부분과 순수 로직을 분리해서, 순수 로직만 테스트한다.

**유닛 테스트 대상 (순수 로직):**
- 다음 발생 시각 계산 — 요일 반복, 1회성, 시간대 변경, 서머타임 경계
- 폴백 체인 결정 — 어떤 소스 조합에서 어떤 순서·동시 재생이 나오는지
- 프리플라이트 판정 — 주어진 시스템 상태에서 어떤 경고가 나오는지
- 옴니박스 판별 규칙 — 입력별 소스 타입 매핑

**프로토콜 뒤로 숨겨 가짜 구현으로 테스트할 대상:**
- `SoundSource` — 실패하는 가짜 소스로 폴백 동작 검증
- `AudioGuard`가 읽고 쓰는 시스템 오디오 상태
- `PowerMatuta`

현재 시각은 주입한다. 테스트가 실제 시계에 의존하지 않게 한다.

**수동 검증이 필요한 것:** 실제 절전 깨우기, 실제 Spotify·Apple Music 재생, 오버레이의 전체화면 점유. 이것들은 자동화하지 않고 체크리스트로 관리한다.

## 11. 범위

### v1에 들어가는 것

- 알람 CRUD, 요일 반복, 켜기/끄기
- 옴니박스 사운드 선택 (6종 소스 전부)
- 폴백 체인 + 백업음 동시 재생
- AudioGuard (출력 기기·볼륨·뮤트)
- 프리플라이트 점검과 원클릭 수정
- 나이트스탠드 전체화면
- 절전 깨우기
- 알람 오버레이, 스페이스바 해제, 마우스 전용 스누즈
- 메뉴바 다음 알람 표시

### 구현 순서

v1 범위가 작지 않으므로 네 단계로 나눈다. 각 단계는 그 자체로 동작하는 앱이어야 한다.

| 단계 | 내용 | 끝났을 때 |
|---|---|---|
| 0. 스파이크 | `IOPMSchedulePowerEvent` 권한 검증 (§9) | 온보딩 설계가 확정됨 |
| 1. 뼈대 | AlarmStore, Scheduler, 목록 창, 편집 시트, 오버레이, 내장 사운드만 | **알람이 울리는 앱**이 된다 |
| 2. 소스 | SoundSource 프로토콜 + 6종 구현, 옴니박스, PlaybackChain | 원하는 음악으로 깨울 수 있다 |
| 3. 신뢰성 | AudioGuard, Preflight, PowerMatuta 통합, 나이트스탠드 | 안 울릴 이유가 사라진다 |

단계 1이 끝난 시점부터 매일 실제로 써보면서 나머지를 만든다. 알람앱은 직접 써보지 않으면 문제를 못 찾는다.

### v1에 넣지 않는 것

- 클록 스타일·테마 다양화
- 아침 루틴 액션 (앱 실행, 탭 복원, 스크립트)
- 수면 타이머 / 백색소음
- 시스템 출력 무음 측정

## 12. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| `IOPMSchedulePowerEvent` 권한 요구 | 온보딩 복잡도 증가 — "쉬움" 원칙에 직접 타격 | 구현 최우선으로 검증. §9의 대안 두 가지 준비 |
| Spotify 앱 제어 불안정 | 알람 소스 하나가 신뢰 불가 | `needsBackupTone = true`로 이미 완화됨. 최악의 경우에도 내장 사운드는 울린다 |
| 오버레이가 다른 전체화면 앱에 가려짐 | 알람이 안 보임 | 창 레벨과 collection behavior로 처리. 소리는 어차피 별개로 울린다 |
| 옴니박스 판별 오작동 | 사용자가 답답함 | 판별 결과를 확정 전 칩으로 보여주고 수정 가능하게 함 |
| 기능 욕심으로 인한 범위 확대 | v1이 안 끝남 | §3.2 비목표와 §4 원칙 4로 방어 |
